# 최적화 계획

## 1. `call_ref-hostfunc-res`의 불필요한 타입 계산

현재 조건 순서에서는 fib의 함수 정보를 가져오고, fib의 타입을 계산한 뒤, 코드가 `HOSTFUNC`인지 검사한다. fib는 일반 Wasm 함수이므로 마지막 검사에서 실패한다. 앞선 타입 계산이 반복해서 낭비된다.

`hint(check_first "hf")` 같은 명시적 순서 지정으로, 함수 정보를 가져온 다음 코드가 `HOSTFUNC`인지 먼저 검사하고, 실제 `HOSTFUNC`일 때만 타입을 계산하는 방안을 실험한다. 이 순서 변경은 **baseline이 아니라 최적화**이며, 원본 조건의 바인딩·부분성·가능한 결과를 보존하는지 확인해야 한다. 특정 Wasm 규칙에 맞춰 번역기가 순서를 추측하면 하드코딩이 될 수 있다. **아이디어:** 원본 조건의 변수 의존성과 안전한 교환 가능성을 정적 분석해 필요한 hint를 제안하거나 부여할 수 있을까? 자동 부여가 정당한지는 별도 검증한다.

## 2. K embedding

현재 main의 heating/cooling은 실행 요청과 hole을 만들고 다시 결합한다. 프로파일에서 관찰한 이 구조적 비용을 줄이기 위해 `opt/kstate-embedding`의 `kstate(C, K)` 방식을 비교한다. 이 방식은 열린 문맥을 `K`에 보관하고, 안쪽 실행을 이어가다가 결과를 원래 문맥에 되돌린다.

opt 브랜치의 코드를 그대로 baseline에 넣지 않는다. 특히 focus 위치와 앞뒤 부분의 역할은 원본 규칙과 명시적 hint에서 얻어야 하며, 특정 Wasm 목록 배치를 전제해서는 안 된다. 적용 가능한 문맥, 닫힌 내부를 다시 열지 않는 조건, 원본 상태와 `kstate`의 대응 관계를 먼저 정한다. 그다음 같은 입력·명령·도구 버전으로 main과 rewrite 수, 시간, 탐색 결과를 비교하고 가능한 결과와 상태 대응을 검증한다. fib에서 줄어든 rewrite 수만으로 의미 보존이나 일반성을 주장하지 않는다.
